# REVIEW.md

Review of the starter `app/main.py`. Line numbers refer to the **starter** file as supplied. Every "how you'd notice"
column was checked by actually running the starter (against an in-memory MongoDB stand-in); numbers are real outputs.

| # | Where (function / line) | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes`, L33-37 | Takes the clock date and time zone from `punch_in` itself (UTC/naive) instead of the IST shift, so the shift start lands on the wrong instant. It also floors to whole minutes *before* comparing, so the "strictly more than 10:00" rule is lost, and it knows nothing about overnight shifts. | Shift 09:30, punch-in 10:05 IST sent as UTC (04:35Z) gives `0`, expected `35`. 09:40:01 gives `0`, expected `10`. | New helpers build the shift start in IST from the attendance date (`shift_window`), compare in whole seconds (`> 600 s`), then floor to minutes. |
| 2 | `compute_work_hours`, L40-41 | Uses Python `round()` on a float: banker's rounding plus binary float error. Seconds are not truncated, and nothing computes `half_day` (R5). | 450 s (0.125 h) returns `0.12`, expected `0.13`. | Exact `Decimal` arithmetic with `ROUND_HALF_UP`; the half-day flag is derived from the *rounded* value (R5). |
| 3 | `compute_overtime`, L44-47 | No 30-minute minimum (R3). Builds the shift end from the record's date, so an overnight shift's end falls on the wrong day. | Out 18:40 on a 18:30 shift gives `10`, expected `0`. Overnight 22:00-06:00, out 06:40 next day gives `1480`, expected `40`. | `shift_window` puts an overnight shift's end on the next day; overtime counts only when floor-minutes >= 30. |
| 4 | `EmployeeIn`, L53-60 | No validation at all: emp_code format, lengths, e-mail, `HH:MM`, a real `joined_on` date, `shift_start != shift_end`. Bad data is stored. | `POST /employees` with name `""`, e-mail `nope`, shift `99:99`, date `nonsense` returns `201`. | Pydantic `Field` constraints and validators that mirror the contract; failures are 422. |
| 5 | `create_employee`, L78-85 | Check-then-insert with no unique index: two simultaneous creates both pass the check. `created_at` is a naive *local* `datetime.now()` and is returned as a datetime, not epoch ms. | Parallel identical POSTs give several `201`s and duplicate documents. | Unique index on `emp_code`; `DuplicateKeyError` becomes 409. `created_at` is UTC, stored as a BSON date and returned as epoch ms. |
| 6 | `list_employees`, L88-96 | `skip = page * page_size` skips the entire first page. `total` counts the whole collection, ignoring the filter. No sort, so the order is unspecified. `page`/`page_size` are not validated. | With 25 employees, page 1 starts at the 21st. `?department=A` reports the unfiltered total. `page_size=0` means "no limit" to MongoDB; a negative one is a server error. | `skip = (page-1)*page_size`; `count_documents(filter)`; sort by `emp_code`; `page >= 1`, `1 <= page_size <= 100` (422 otherwise). |
| 7 | `punch_in`, L101 and L113 | The employee lookup is never checked: an unknown `emp_code` makes `emp["shift_start"]` fail with `TypeError`. | `POST /attendance/punch-in` for an unknown employee returns `500`; the contract says `404`. | `get_employee_or_404` before any use. |
| 8 | `punch_in`, L102-103 | `datetime.fromtimestamp(ms/1000)` uses the *server's local* zone and returns a naive value. `if body.punched_at` treats `0` as "not sent". Seconds are not truncated. `date` is `ts.date()` in server time, not IST (R1), and overnight shifts are ignored. | Moves with the server's time zone. A 01:00 IST punch-in gets the previous date on a UTC server. | Epoch ms -> aware UTC datetime truncated to seconds; `attendance_date()` converts to IST and applies the overnight rule (R1); "not sent" is `is None`. |
| 9 | `PunchInIn`, L63-66 | `status` is a free string and `punched_at` accepts anything int-like. | `status: "GARBAGE"` (or `ABSENT`) returns `201` and stores a bogus record. Seconds-looking and float timestamps are accepted. | `status` is a `Literal` of the 3 presence values; `punched_at` is a strict int in `[1e11, 4.1e12]`, so floats, strings, `null` and seconds are 422. |
| 10 | `punch_in`, L104-105 and L118 | Check-then-insert with no unique `(emp_code, date)` index: two simultaneous punch-ins both pass the check and both insert. | Parallel identical punch-ins produce several `201`s and duplicate records. | Unique index `(emp_code, date)`; a single `insert_one`; `DuplicateKeyError` -> 409. |
| 11 | `punch_in`, L119-121 | Response contains `id` (the ObjectId, which must never leave the API) and `punch_in` as a datetime object, not epoch ms. | Response keys include `id`; the contract has no such field. | `serialize_record()` builds the response from an explicit field list and converts instants to epoch ms. |
| 12 | `list_attendance`, L144-150 | `list(find(q))` loads the **whole** matching collection into memory, sorts in Python and slices. No indexes. No `emp_code` tie-break in the sort. `page=0` slices backwards. `date_from > date_to` silently returns empty. Legacy docs (no `half_day`/`history`) are returned as stored. Leaks `id`/raw datetimes. | At 100k records every request is O(n) in memory and time; `page=0` returns `200` with wrong data. | Database-side `sort(date desc, emp_code asc)` + `skip`/`limit` backed by indexes; `count_documents`; validation (422) for dates, status, paging; defaults for legacy fields. |
| 13 | `health`, L72-74 | Always returns `ok`, even if MongoDB is down; the runner would start testing a dead service. | Stop MongoDB: `/health` still says `200`. | Pings MongoDB; any failure -> `503`. |
| 14 | module top, L22-23 | `MongoClient` without `tz_aware` (naive datetimes everywhere), 30 s default server-selection timeout (a down database freezes requests), no index creation, no `close()` on shutdown. A hard-coded fallback DB name. | Naive/aware comparison errors; first request hangs ~30 s without a database. | `tz_aware=True`, 5 s timeout, indexes created in the startup `lifespan` (idempotent, retried from `/health`), `client.close()` on shutdown, a handler turning any `PyMongoError` into `503` instead of a raw 500. |
| 15 | all endpoints | Any database error escapes as an unhandled 500 with no message. | Kill MongoDB mid-request. | Global `PyMongoError` handler returns `503 {"detail": "database unavailable"}`; nothing is swallowed into a success response. |

## Looked at and decided it was fine

* **String date comparison** (`date >= "2026-07-01"`) in `list_attendance`: zero-padded `YYYY-MM-DD` strings sort the same
  as dates, so range queries on the stored string are correct and index-friendly. I kept this approach.
* **`load_dotenv()`**: by default it does *not* override variables already present in the environment, so real
  environment variables correctly win over `.env`.
* **`doc.pop("_id", None)` after `insert_one`** in `create_employee`: removing the internal id from the response is
  right (I kept the idea, but build the response from an explicit field list).
* **`IST = timezone(timedelta(hours=5, minutes=30))`**: correct (IST has no daylight saving), reused as is.
* **Response status `201` on creation** and `emp_code` as the lookup key (never `_id`): both match the contract.
* **Pagination arithmetic in `list_attendance`** (`(page-1)*page_size`) is right; only `list_employees` has the
  off-by-one-page bug.
